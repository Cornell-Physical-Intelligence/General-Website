## Confirmed defects and audit gaps

### Missing www DNS alias: DNS repaired, HTTPS not yet complete

Public DNS returned no CNAME for `www.cornellphysicalintelligence.com`, and
HTTPS failed to resolve. Squarespace DNS UI confirmed no `www` record.
The apex's four GitHub Pages A records were present. Existing wiki, tm,
mail, verification, and nameserver settings must remain untouched.

Authorized repair: add only `www` CNAME to
`Cornell-Physical-Intelligence.github.io` (no scheme or repository path).
GitHub Pages already has the apex as its canonical custom domain with HTTPS
enforced. The user reauthenticated, and at approximately 13:25 UTC the
single CNAME was saved with the default 4-hour TTL. Authoritative DNS and
Cloudflare's public resolver returned the correct target. The DNS UI
confirmed that the existing records remained unchanged.

Verified HTTP www redirects with status 301 to the HTTPS apex, preserving
both `/work/` and a test query string. The apex itself remains HTTP 200
over valid HTTPS. GitHub's DNS health endpoint reports both apex and www
valid and HTTPS-eligible.

HTTPS www still fails certificate hostname validation. GitHub reports an
approved certificate covering only the apex, expiring November 27, 2026.
Re-saved the same apex CNAME and `https_enforced=true` once through the
documented GitHub Pages update API; the main/docs publishing source and
canonical domain were preserved. This did not immediately change the
certificate's coverage. No TLS bypass, domain removal, or disabling of
HTTPS was performed. The existing daily automation now tracks the TLS
issue instead of the resolved login blocker.

The remaining blocker is certificate coverage for www. Do not call the
whole alias repair complete until HTTPS and its redirects verify. If
GitHub does not provision coverage, discuss any domain removal/re-addition
with the user before risking the working canonical site's availability.

The existing live SEO verifier checks apex HTTP and slash normalization,
but does not test `www`, so it can pass while that alias is broken.

### Legacy visible SEO pages remain reachable

`/about-cupi/` and `/faq/` return HTTP 200 and remain in the sitemap. Removing
their navigation links did not remove the pages. Their origin is visible
in commits `7333f54` (about ranking page) and `fe5b3c8` (FAQ page).
Existing visible keyword-oriented prose is in `src/pages/AboutCupi.jsx`
and `src/pages/Faq.jsx`. No removal or rewrite was performed because the
latest instruction freezes content on every platform.

### Separate fallback copy has drifted

`src/seoBuild.js` supplies a distinct no-JavaScript fallback. For example,
its sponsor list omits Onshape even though `src/pages/Sponsors.jsx` includes
it. Other fallback prose is not an exact copy of the normal React page.
The fallback is hidden with JavaScript enabled and shown through noscript;
Googlebot/default HTML equality alone does not prove rendered parity.
This is a maintenance/content-consistency finding, not evidence of a
Google penalty. No fallback copy was changed.

### Stale search snippets are not necessarily live defects

The teammanager Vercel login already returns `noindex, follow`; its older
Google snippet is not permission for repeated changes or removal requests.
The local tm checkout was older than the live page and must not be deployed
as a purported SEO fix.
